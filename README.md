# Travel

My Travel Hub의 여행 정보를 읽는 React 앱입니다. 여행 목록은 공개하고, 상세는 여행별 숫자 4자리 PIN으로 잠급니다. 여행 데이터는 Notion에서 관리합니다.

## 로컬 실행

Node.js 24에서 아래 명령을 실행합니다.

```sh
npm ci
npm run dev
npm run lint
npm run build
npm test
```

테스트는 임시 인증 값을 생성하고 루프백에서 Vite HTTP 서버를 시작합니다. Notion 응답은 목을 사용하므로 테스트에 실제 토큰이 필요 없습니다.

## Vercel 배포

Vercel에서 Vite 프레임워크, 빌드 명령 `npm run build`, 출력 폴더 `dist`를 사용합니다. Vite 개발 미들웨어와 Vercel Node 함수가 조회와 PIN 인증 API를 제공합니다. 정적 호스팅이나 `vite preview`에서는 API가 실행되지 않습니다.

## P1 Notion My Travel Hub 읽기 전용 연동

생성, 수정, 삭제, 체크 상태 변경, 영수증 첨부는 모두 Notion에서 합니다. 앱에서는 조회와 필터링을 제공하며, 오늘 일정 상세에서 해당 일정의 Notion 원본을 열 수 있습니다.

### 오늘 일정 대시보드

홈은 여행 현지 날짜를 기준으로 진행 중인 여행 또는 다음 예정 여행을 표시합니다. 오늘 일정 탭에서는 여행 기간 안에서 날짜를 이동하고, PIN으로 열린 상세 화면에서 해당 날짜의 일정과 다음 시작 일정을 확인할 수 있습니다.

| 화면 | 확인한 Notion 필드 |
| --- | --- |
| 활성 여행과 날짜 경계 | 여행 마스터의 `여행명`, `여행지`, `여행기간`, `상태` |
| 타임라인과 상세 | 여행 일정의 `일정명`, `일시`(시작·종료·시간대), `구분`, `장소`, `진행상태`, `메모`, `지도 URL` 및 일정 페이지 링크 |
| 관련 예약 | 여행 일정의 `관련 예약` 관계 및 같은 여행 예약 관리의 `예약명`, `예약상태` |

여행 마스터에는 시간대 속성이 없어 기존 상하이 여행은 `Asia/Shanghai`, 마카오·광저우 여행은 `Asia/Macau`를 기본값으로 매핑합니다. 새 여행은 기본 시간대를 추가하기 전까지 화면에서 시간대 확인이 필요하다고 표시합니다. 일정의 명시된 시간대 또는 오프셋은 기본값보다 우선합니다. 종일 여부와 별도 주소 속성은 확인한 스키마에 없으므로 날짜만 저장된 일정은 시간 미정으로 표시하고 장소는 원본 문자열을 사용합니다.

### 확인한 데이터 소스

My Travel Hub의 DB 8개를 조회해 아래 구조를 확인했습니다. 모든 하위 DB에는 여행 마스터를 가리키는 `여행` 관계가 있습니다.

| DB | 앱에서 읽을 항목 |
| --- | --- |
| 여행 마스터 | 여행명, 여행지, 여행기간, 상태, 메모, 총예산·총지출·잔여예산 |
| 여행 일정 | 일정명, 일시, 구분, 장소, 진행상태 |
| 예약 관리 | 예약명, 예약유형, 예약상태, 이용일, 결제상태 |
| 예산 관리 | 예산항목, 분류, 예산 KRW, 사용금액, 잔액 |
| 지출 내역 | 지출명, 분류, 비용구분, 결제일, 결제자, 결제수단, 정산여부, 통화, 현지 금액, 원화 확정액, 집계 금액 |
| 영수증 관리 | 영수증명, 처리상태, 연결된 지출, Notion 페이지 링크 |
| 여행 체크리스트 | 할 일, 분류, 상태, 단계, 기한 |
| 쇼핑 리스트 | 품목, 분류, 유형, 상태, 우선순위, 구매방법, 매장, 위치, 추천품목, 구매예정일, 단계, 기한, 메모 |

여행 메모와 일정 장소는 여행 마스터와 일정에서 읽고, 정보가 비어 있으면 빈 상태를 표시합니다. 예산과 지출 합계는 Notion의 KRW 롤업·수식 값을 기준으로 표시합니다. 현지 금액과 통화는 별도로 표시하고 P0의 JPY 환율로 다시 계산하지 않습니다.

### 공개 목록과 여행별 PIN

1. `GET /api/trips`는 로그인 없이 모든 여행의 ID, 여행명, 여행지, 여행기간, 상태만 반환합니다. 메모와 예산 등 상세 데이터는 별도 API에서 제공합니다.
2. `POST /api/trips/:tripId`는 해당 여행의 PIN만 확인합니다. 일치하면 여행별로 서명된 30분짜리 HttpOnly 쿠키를 발급합니다. 운영 쿠키에는 Secure가 적용됩니다. PIN을 바꾸거나 제거하면 기존 쿠키도 무효화됩니다.
3. `GET /api/trips/:tripId`는 해당 여행의 유효한 쿠키가 필요합니다. 여행 마스터 소속을 확인하고, 하위 데이터는 `여행` 관계가 정확히 해당 여행을 가리키는 경우만 반환합니다. 상세 지출에는 결제자와 정산여부를 포함합니다. 응답은 저장되지 않도록 `Cache-Control: private, no-store`를 사용하며 예약번호와 영수증 이미지 URL은 제외합니다.
4. 모든 서버 인스턴스가 환경과 여행별로 같은 Redis 카운터를 사용합니다. 첫 입력부터 1시간 동안 성공·실패 합계 10회를 허용하며, Redis를 사용할 수 없으면 새 PIN 인증은 실패합니다. 한 여행의 제한이 다른 여행에 적용되지는 않습니다. 4자리 PIN은 단순 열람 제한이며, 해당 여행의 시도 한도가 소진되면 올바른 PIN을 가진 사용자도 만료까지 기다려야 합니다.

### PIN과 요청 제한 설정

`.env.example`을 참고해 로컬에서는 `.env.local`에, Vercel에서는 적용할 Preview 또는 Production의 서버 환경변수에 아래 값을 등록합니다.

| 환경변수 | 설정 |
| --- | --- |
| `TRAVEL_DETAIL_PINS` | Notion **여행 페이지 ID**를 키로, 4자리 PIN 문자열을 값으로 둔 JSON. 예시 `{"00000000-0000-4000-8000-000000000001":"0427"}`. 하이픈이 있는 소문자 UUID를 사용합니다. |
| `TRAVEL_DETAIL_ADDITIONAL_PINS` | 기존 Secret 값을 확인할 수 없을 때 새 여행만 추가하는 선택 JSON 매핑. 형식은 `TRAVEL_DETAIL_PINS`와 같습니다. 기존 매핑에 없는 여행에만 적용되며, 기존 여행의 PIN을 변경하거나 덮어쓰지 않습니다. |
| `TRAVEL_DETAIL_PIN_<여행ID>` | 두 JSON 매핑의 원본을 모를 때 새 여행에만 사용하는 선택 Secret. 여행 페이지 UUID의 하이픈을 제거하고 대문자로 바꾼 값을 접미사로 사용하며, 값은 4자리 숫자 문자열입니다. 기존 두 매핑이 우선하므로 다른 여행 설정을 덮어쓰지 않습니다. |
| `SESSION_SECRET` | 기존 서버 서명 키를 사용하거나 32자 이상의 별도 무작위 키를 생성합니다. |
| `TRAVEL_REDIS_REST_URL` | Upstash Redis HTTPS REST 엔드포인트. |
| `TRAVEL_REDIS_REST_TOKEN` | 카운터 갱신이 가능한 Upstash REST 토큰. 기존 `UPSTASH_REDIS_REST_TOKEN`도 사용할 수 있습니다. |

PIN 매핑, 서명 키, Redis 토큰은 비밀 환경변수로 저장합니다. 새 여행은 공개 목록에 바로 나타납니다. Notion에서 `PIN 방식 = 시작일 자동`을 선택하면 시작일 MMDD로 상세를 열 수 있으며, 여행별 PIN 환경변수 추가·재배포가 필요 없습니다. 명시 PIN 방식은 기존 환경변수 등록 절차를 사용합니다. 동일 PIN을 여러 여행에 재사용하면 사용자가 각각에 같은 PIN을 직접 입력할 수 있으므로 여행별로 다른 값을 사용합니다.

기존 `TRAVEL_DETAIL_PINS`가 공개할 수 없는 Secret이고 원본을 찾을 수 없다면 해당 변수는 그대로 둡니다. 위 추가 매핑을 지원하는 코드를 배포하고, 새 여행만 `TRAVEL_DETAIL_ADDITIONAL_PINS`에 등록한 뒤 Production을 재배포합니다. 추가 매핑도 Secret으로 저장하며 실제 PIN은 소스에 기록하지 않습니다. 추가 변수의 JSON이 잘못되어도 기존 매핑에 있는 여행은 영향을 받지 않습니다.

### 앱 연동 설정과 검증

1. My Travel Hub에 연결할 Notion 내부 통합에 콘텐츠 읽기 권한을 부여합니다. 통합에 아래 데이터 소스의 상위 DB 접근을 부여합니다.
2. 로컬에서는 `.env.local`에, 배포 환경에서는 Vercel 서버 환경변수에 `NOTION_TRAVEL_TOKEN`을 등록합니다. 다음 키에는 각 DB의 **데이터 소스 ID**를 넣습니다. Notion API에서 DB를 조회하면 응답의 `data_sources`에서 확인할 수 있습니다.

   | 환경변수 | Notion DB |
   | --- | --- |
   | `NOTION_TRAVEL_TRIPS_SOURCE_ID` | 여행 마스터 |
   | `NOTION_TRAVEL_SCHEDULE_SOURCE_ID` | 여행 일정 |
   | `NOTION_TRAVEL_BOOKINGS_SOURCE_ID` | 예약 관리 |
   | `NOTION_TRAVEL_BUDGETS_SOURCE_ID` | 예산 관리 |
   | `NOTION_TRAVEL_EXPENSES_SOURCE_ID` | 지출 내역 |
   | `NOTION_TRAVEL_RECEIPTS_SOURCE_ID` | 영수증 관리 |
   | `NOTION_TRAVEL_CHECKLIST_SOURCE_ID` | 여행 체크리스트 |
   | `NOTION_TRAVEL_SHOPPING_SOURCE_ID` | 쇼핑 리스트. 미설정 시 기존 여행 상세는 열리며 쇼핑 탭에 연결 안내가 표시됩니다. |
   | `NOTION_TRAVEL_CITIES_SOURCE_ID` | 도시 DB. `41e6d8c5-8de1-81f4-a824-000b11c7a3c6` (도시 날씨·시간대에 필요) |
   | `NOTION_TRAVEL_INFO_SOURCE_ID` | 여행지 정보 (선택). 기존 데이터 소스 ID: `846412f2-7bc7-499b-b36c-fd84b79a991e`. 미설정이어도 날씨는 조회됩니다. |
   | `NOTION_TRAVEL_PHOTOS_SOURCE_ID` | 여행 사진 (선택). 데이터 소스 ID: `4196d8c5-8de1-8173-abdf-000b5b435da0`. |

3. 체크리스트와 쇼핑 리스트는 별도의 DB에서 조회합니다. 체크리스트 DB에서 `분류`가 `쇼핑`인 항목은 앱의 쇼핑 리스트에 표시합니다. 두 DB 모두 각 항목의 `여행` 관계에 여행 마스터의 여행 한 건을 연결합니다. DB에서 속성명을 바꾸면 서버 매핑을 같이 갱신해야 합니다. 계산값을 Notion이 제공하지 않으면 화면에는 대시를 표시합니다.
4. 목 테스트로 공개 목록, PIN 검증·만료·여행 간 격리, 시도 제한 장애, 쓰기 요청 거부, Notion 관계 검증과 페이지네이션을 확인합니다. 실제 배포에서 PIN 설정 후 두 여행의 상세가 각각 열리는지, Notion 변경이 새로고침에 반영되는지 확인합니다.

`정보` 탭은 여행 PIN을 확인한 뒤 선택한 여행과 도시의 지역 정보를 읽습니다. Vercel에 데이터 소스 ID를 설정하고 기존 Notion 통합에 해당 DB의 읽기 권한이 있는지 확인합니다. 앱에서 Notion에 쓰지 않습니다.

날씨는 앱 서버에서 도시 대표 좌표로 [Open-Meteo](https://open-meteo.com/en/docs)에 요청합니다. Vercel은 도시별 응답을 5분간 캐시합니다. 배포 전 [무료 API 사용 조건](https://open-meteo.com/en/terms)을 확인하고 운영 중 호출량과 오류를 확인합니다.

### 여행 사진

기존 Notion 읽기 통합에 여행 사진 DB를 공유하고 `NOTION_TRAVEL_PHOTOS_SOURCE_ID`를 설정합니다. 여행 사진 DB에서 `여행` 관계를 한 건만 연결하고 `사진` 속성에 JPEG, PNG, WebP, GIF, AVIF 또는 HEIC를 직접 첨부합니다. HEIC는 원본을 Notion에 보존하고 화면 표시용 JPEG로 변환합니다. HEIC 변환 한도는 파일당 24 MiB·5천만 픽셀이며 표시용 이미지의 긴 변은 최대 2048px입니다. 외부 링크 파일은 갤러리에서 이미지 대신 안내를 표시합니다. 여러 파일을 첨부하면 같은 캡션으로 각각 표시됩니다.

`표시 순서`가 있는 사진을 먼저 정렬하고, 같은 순서에서는 촬영일과 레코드 ID를 사용합니다. 대표 사진을 지정하지 않으면 표시할 수 있는 첫 사진을 씁니다. 사진 목록과 이미지 요청에 각각 여행 PIN 세션이 필요하며, 서버는 원본 Notion 파일 URL을 브라우저에 전달하지 않습니다. 파일 URL이 만료됐거나 파일 서버가 401·403·404를 반환하면 Notion에서 다시 조회합니다.

공개 여행 목록은 동일한 기준의 대표 사진 한 장을 커버로 표시합니다. 이 커버는 PIN 없이 볼 수 있으며 서버에서 긴 변 최대 800px의 JPEG로 변환하고 위치 등 이미지 메타데이터를 제거합니다. 사진이 없거나 변환에 실패하면 기존 커버를 표시합니다.

브라우저에서 예제 데이터로 확인하려면 개발 서버를 `npm run dev -- --host 127.0.0.1 --port 4179 --strictPort`로 실행한 뒤 `playwright-cli open about:blank --browser=chrome` 및 `playwright-cli run-code --filename=qa/travel-gallery.playwright.mjs`를 실행합니다. 실제 Notion에 연결할 때는 사진을 한 장 등록하고 해당 여행의 PIN으로 상세와 이미지를 확인합니다.


### Notion 도시 관리와 정보 탭

도시 DB와 여행 마스터의 `도시` 관계를 읽습니다. 앱은 Notion 데이터를 생성·수정·삭제하지 않습니다.

1. Vercel Preview/Production에 `NOTION_TRAVEL_CITIES_SOURCE_ID=41e6d8c5-8de1-81f4-a824-000b11c7a3c6`를 등록합니다. DB 페이지 ID가 아닌 data source ID입니다.
2. 기존 `NOTION_TRAVEL_TOKEN`의 integration에 도시 DB 읽기 권한을 부여합니다. 연결된 Notion 도구와 앱 integration의 권한은 서로 다를 수 있습니다. 기존 여행·여행지 정보 DB 변수는 유지합니다.
3. 새 도시를 도시 DB에 등록합니다. `도시명`(title), 고유 `도시 코드`(rich_text, 예: `JP_TOKYO`), `국가 코드`(두 자리 대문자), `시간대`(IANA, 예: `Asia/Tokyo`), `위도`/`경도`(number), `활성`(checkbox)을 채웁니다. 좌표는 날씨 대표점으로만 사용합니다.
4. 여행 마스터의 `도시` 관계에 해당 도시를 연결합니다. 신규 여행에서 `PIN 방식 = 시작일 자동`을 선택하면 날짜 기반 PIN을 사용합니다. 기존 PIN 방식은 Vercel에 명시 PIN을 별도로 등록합니다. 도시 관계 자체는 PIN 방식을 바꾸지 않습니다.
5. 안내 글은 여행지 정보 DB에서 `여행`과 `도시`를 각각 하나씩 연결하고 기존 네 분류를 사용합니다. 기존 `도시 코드`가 있으면 관계의 코드와 일치해야 합니다. 새 도시에서는 기존 select를 반드시 추가할 필요는 없습니다. 기존 속성/12건 안내는 삭제하지 않습니다.
6. 앱에서 여행 새로고침을 누릅니다. 단일 도시는 바로 표시하고 복수 도시는 선택 버튼을 제공합니다. 부산·목포처럼 안내 글이 없으면 날씨와 별개로 미등록 안내를 표시합니다. 옷차림 문구는 자동 생성하지 않습니다.

도시 마스터는 서버 인스턴스별 5분 캐시입니다. Notion 수정은 만료 후 반영되며 실패한 조회는 캐시하지 않습니다. 날씨 응답은 Vercel CDN에서 5분(재검증 중 최대 1분 추가), 브라우저에서는 기존 30분 갱신 주기를 사용합니다. 좌표/시간대 변경 후 여행 새로고침으로 도시 설정을 다시 읽으면 브라우저 날씨 캐시 키도 바뀝니다. CDN에 이전 응답이 남는 동안은 만료 후 날씨 새로고침으로 확인합니다. 코드 수정/재배포는 필요 없습니다.

좌표 범위·유효 IANA 시간대·활성 상태·코드 중복을 서버에서 검증합니다. 도시 데이터 오류는 임의 도시로 대체하지 않으며 다른 여행 탭은 계속 이용할 수 있습니다. `city_data_invalid`는 중복 코드/필수값, `cities_not_configured`는 환경변수, `cities_access_denied`는 앱 integration 공유 권한, `city_relation_invalid`는 여행의 도시 관계(누락/잘린 관계)를 확인합니다. 관계가 `has_more=true`이면 부분 목록 대신 안전하게 실패합니다. 비활성/삭제된 도시는 목록과 신규 날씨 조회에서 제외됩니다.

오늘 일정과 지출 날짜 계산은 도시의 시간대를 사용하며 일정 자체에 명시된 시간대/오프셋은 보존합니다. 마카오·광저우처럼 여행 기간 내 오프셋이 같은 복수 도시는 기존 동작을 유지합니다. 오프셋이 다른 복수 도시는 기준 시간대를 임의로 선택하지 않습니다. 이 경우 여행 마스터에 `기준 도시`를 추가하는 후속 스키마 설계가 필요하며 이번 작업에서 DB 구조를 변경하지 않습니다. 공개 여행 목록은 오늘 대시보드에 필요한 `calendarZone`만 추가하고 도시 관계 ID·상세 도시 배열은 PIN 뒤에서 제공합니다.

배포 전 `npm ci`, `npm run lint`, `npm test`, `npm run build`를 실행합니다. 운영 환경에서는 목포·부산 날씨, 마카오·광저우 도시 전환, 상하이 안내, 비인증 상세 차단을 확인합니다. 문제가 있으면 이전 Vercel 운영 배포로 롤백하며 Notion 기존 데이터와 관계는 유지합니다.


### 일정 동선 지도

일정 탭의 기본 타임라인을 유지하며 `동선 지도`에서 날짜별/전체 방문 번호와 직선 점선을 표시합니다. 타임라인과 오늘 일정은 장소명 아래에 `활동`을 구분해 표시하고 장소·활동 검색을 지원합니다(검색은 일정 타임라인 대상). 메모·주소·관련 예약·지도/원본 링크는 상세에서 확인합니다.

v1.1은 방문 그룹과 원본 일정을 분리합니다. 같은 날 연속되는 동일 시설만 묶고 하위 활동/원본 ID를 모두 보존하며, A→B→A는 서로 다른 방문입니다. 정규화한 정확한 이름/주소 또는 명시된 시설 소속과 같은 좌표로 확인하며, 가깝거나 좌표가 같다는 이유만으로 다른 상호를 합치지 않습니다. `→` 등 복수 장소 이동 구간은 별도 기록으로 표시하고 번호/마커를 만들지 않습니다. 양쪽의 인접 방문이 확인될 때만 연결을 유지하며, 알 수 없는 경유지/누락 방문을 건너뛰지 않습니다. 단일 공항·역·국경 방문은 구분이 이동이어도 지도에 포함합니다. 집/귀가로만 식별되는 사적 장소는 기본 지도에서 제외하고 원본 타임라인에 유지합니다.

하루의 취소·이동 구간·사적 장소를 제외한 모든 방문 후보에 양의 안전 정수 `동선 순서`가 중복 없이 있으면 그 순서로 그룹화 후 1부터 번호를 표시합니다. 시간 미정/종일도 계획 동선에 포함할 수 있지만 시간을 만들어내지 않습니다. 일부 순서만 입력된 날은 시각 순서를 우선하며 시간 미정 후보는 보조 표시합니다. 중복 순서·시각 충돌·미확정 시간 때문에 상대 순서를 확정할 수 없는 날은 경고하고 연결을 보수적으로 생략합니다. 동시각 다른 시설에 닿는 선, 위치 누락 구간 및 날짜 사이 선은 표시하지 않습니다. 완료는 포함하고 취소는 원본에 남깁니다. 날짜 미정은 전체 목록에 표시합니다. 보기와 날짜는 여행별 sessionStorage에 저장하며 기존 오늘 일정의 hash 날짜와 독립적입니다. 여행 ID나 장소를 코드에 등록하지 않습니다.

#### Notion 좌표 준비

이번 구현은 DB를 수정하지 않았습니다. 운영 일정 DB의 `활동`(rich_text), `동선 순서`(Number), `위도`/`경도`(Number) 추가를 확인했습니다. 네 속성 모두 선택적으로 읽으며 없는 기존 행도 조회됩니다. 활동은 장소와 별도로 입력하고, 시간 미정 순서를 확정할 때는 해당 날짜의 모든 방문 후보에 10, 20…처럼 중복 없는 양의 안전 정수를 입력합니다(이동 구간·취소·집은 대상에서 제외).

각 일정의 **확인된 WGS84** 좌표를 입력합니다. 두 값 모두 숫자여야 하며 위도 -90~90, 경도 -180~180이고 0도 유효합니다. 지도 투영 범위를 벗어나는 극지방은 목록에 사유를 표시합니다. 속성/값이 없어도 상세 API와 타임라인은 정상 작동합니다. 도시 DB의 날씨 대표 좌표를 개별 일정 위치로 대신 사용하지 않습니다.

Google/중국 지도에서 복사한 좌표의 좌표계를 먼저 확인하세요. GCJ-02/BD-09를 WGS84로 간주하거나 자동 변환하지 않습니다. 기존 DB에 선택적 `좌표계` select가 있다면 값이 `WGS84`인 경우만 허용합니다(필수 신규 속성이 아닙니다).

숫자 속성이 없을 때는 `https://www.google.com/maps/search/?api=1&query=위도,경도#WGS84` 형태만 좌표 후보로 읽습니다. 마지막 `#WGS84`는 운영자가 좌표계를 확인했다는 **앱 자체 규약**이며 Google의 공식 좌표계 보증이 아닙니다. 카메라 중심 `@`, 장소명, 길찾기 시작/도착, 단축 링크는 좌표로 추측하지 않고 기존 외부 지도 링크로만 제공합니다. 가장 권장하는 방식은 숫자 속성 입력입니다. 등록 후 앱의 `새로고침`으로 다시 읽습니다.

#### 지도 공급자와 설정

React 19에 추가 래퍼 없이 [Leaflet 1.9.4](https://leafletjs.com/reference-1.9.4.html)를 effect/ref로 연결했습니다. 지도 선택 시에만 모듈과 타일을 불러옵니다. 기본은 OpenStreetMap 표준 타일이며 출처를 표시하고 브라우저 캐시를 따릅니다. 길찾기·거리·ETA·GPS·지오코딩 요청은 없습니다.

기본 공급자는 별도 환경변수가 필요 없습니다. 교체할 경우 빌드 환경에 공개 변수 `VITE_ROUTE_TILE_URL`(HTTPS, `{z}`, `{x}`, `{y}` 포함), `VITE_ROUTE_TILE_ATTRIBUTION`, `VITE_ROUTE_TILE_ATTRIBUTION_URL`(HTTPS)을 설정하고 다시 빌드합니다. 키가 필요하다면 브라우저에 공개해도 되는 도메인 제한 키만 공급자의 정책대로 사용하세요. 비밀 키를 VITE 변수에 넣지 않습니다. WGS84 위치와 정합되는 Web Mercator XYZ 타일만 사용합니다.

[OSM 타일 정책](https://operations.osmfoundation.org/policies/tiles/)에 따라 visible attribution, 정상 Referer, 캐시를 유지하며 사전 다운로드/오프라인 저장/대량 수집은 하지 않습니다. 표준 타일에는 SLA가 없고 차단될 수 있으므로 무료·무제한이나 중국 현지 정상 동작을 보장하지 않습니다. 운영 트래픽이 커지거나 현지 연결성이 부족하면 해당 용도를 허용하는 공급자의 요금·약관을 확인해 교체합니다. 타일 요청에는 조회 영역과 IP가 노출될 수 있지만 앱이 일정 제목·메모·PIN·Notion 토큰을 전달하지 않습니다. 인증된 상세 좌표는 기존 PIN 보호 응답에만 추가하며 공개 여행 목록에는 포함하지 않습니다.

검증 결과와 미검증 범위는 [v1.1 동선 지도 QA 보고서](docs/route-map-v1.1-qa.md)를 참고하세요. [v1.0 보고서](docs/route-map-qa.md)는 당시 검증 기록으로 보존합니다.

타임라인 추가 개정은 [통합 명세 §13](docs/Travel_Route_Map_v1.1_Codex.md)에 반영했습니다. 일정/오늘 일정은 지도 모델에서 생성한 같은 방문 그룹을 공통 `ScheduleTimeline`에서 렌더링합니다. 연속 활동은 한 카드, 이동은 작은 연결 행, 위치가 불명확한 기록은 미확정 기록으로 보존합니다. 주소·중복 장소명은 접힌 카드에서 숨기고 상세에 메모·예약·상태와 함께 제공합니다. 날짜는 일자 헤더에만, 카드에는 실제 시간 범위나 시간 미정만 표시합니다. 활동 검색은 그룹 생성 후 적용해 원래 그룹과 번호를 유지합니다.

### 시작일 MMDD 자동 PIN (참여자용)

여행 마스터에 `PIN 방식` select를 추가했습니다. `시작일 자동`, `기존 PIN`, `접근 차단` 중 선택합니다. 기존 여행의 날짜·정책 값·명시 PIN은 변경하지 않았습니다. 기본값이 비어 있으면 기존 명시 PIN만 허용하고 자동으로 열지 않습니다.

신규 여행은 `PIN 방식 = 시작일 자동`을 선택하고 `여행기간`을 날짜만으로 입력합니다. 예를 들어 `2027-03-09`의 코드는 문자열 `0309`입니다. 코드 최초 배포 후에는 여행별 PIN 환경변수 추가와 재배포가 필요 없습니다. **관리자 로그인은 요구하지 않습니다.** 이는 첨부 설계의 관리자 필수 조건을 제외하라는 사용자의 변경 요청을 반영한 정책입니다.

시작일이 공개 목록에 있으므로 MMDD는 비밀이 아닙니다. 여행 참여자뿐 아니라 공개 일정을 아는 사람도 코드를 유추하여 상세를 열 수 있습니다. 개인 정보·결제 관련 정보처럼 강한 접근 제한이 필요한 여행에는 날짜와 무관한 기존 명시 PIN을 유지합니다. Redis 제한으로 공개 날짜에서 파생된 코드의 비밀성을 보완할 수는 없습니다.

적용 순서:
1. `접근 차단`은 명시 PIN이 있어도 보호된 상세를 차단합니다. 공개 여행 목록과 공개 커버는 기존 공개 범위를 유지합니다.
2. 그 외에는 `TRAVEL_DETAIL_PINS` → `TRAVEL_DETAIL_ADDITIONAL_PINS` → `TRAVEL_DETAIL_PIN_<여행ID>`의 순서로 기존 명시 PIN을 보존합니다. 잘못된 명시 값/JSON을 자동 PIN으로 대체하지 않습니다.
3. 명시 PIN이 없는 여행에만 `시작일 자동` 정책과 검증된 시작일을 적용합니다. 정책이 없거나 알 수 없으면 잠급니다.

자동 날짜는 `1000-01-01`~`9999-12-31` 범위의 실제 `YYYY-MM-DD`만 허용합니다. 윤년을 검증하고 종료일이 앞선 범위는 거절합니다. 시각이 포함된 Notion DATE는 자동 PIN 대상에서 제외하므로 날짜 전용으로 수정해야 합니다. 브라우저/서버 시간대로 날짜를 변환하지 않습니다.

자동 PIN 쿠키는 30분, HttpOnly, SameSite=Strict, 운영 Secure와 여행별 Path를 유지합니다. v2 서명은 여행 ID·모드·시작일 전체·만료 시각과 연결하되 쿠키에는 날짜/PIN 원문을 넣지 않습니다. 시작 연도만 바뀌어 코드가 같아도 이전 세션을 무효화합니다. 정책 차단/수동 방식 전환, 명시 PIN 추가 시에도 자동 세션을 거절합니다. 기존 명시 PIN 쿠키의 v1 서명은 그대로 지원합니다.

변조/만료 쿠키는 Notion 요청 전에 거절합니다. POST는 Origin·JSON·네 자리 형식을 검증하고 Redis 시도 제한을 먼저 적용한 뒤 해당 여행의 Notion 출처·정책·시작일을 읽습니다. 보호된 GET은 유효 서명 쿠키를 선검증한 뒤 현재 여행 메타데이터를 매 요청 다시 읽으므로 정책/날짜 캐시로 인한 유예를 두지 않습니다. Notion 장애·잘못된 데이터 소스·보관/삭제된 페이지에서는 상세를 반환하지 않습니다. PIN 정책과 코드는 공개 목록/상세 응답에 추가하지 않습니다.

추가 환경변수는 없습니다. 기존 `SESSION_SECRET`, Notion 연결과 Redis 설정은 필요하며 관리자 전용 기능의 `ADMIN_PASSWORD_HASH`와 참여자 자동 PIN은 독립적입니다. 이번 작업은 앱에서 Notion을 쓰는 기능을 추가하지 않습니다.

Notion 기본 템플릿의 자동 적용은 연결 도구에서 설정하지 않았습니다. 새 여행마다 `시작일 자동`을 선택하거나, Notion 여행 마스터의 새 항목 템플릿에 이 값을 저장하고 기본 템플릿으로 지정합니다. 템플릿 확인 전 미설정 여행을 자동으로 여는 동작은 없습니다. 롤백은 `접근 차단`/`기존 PIN` 정책으로 차단하거나 이전 Vercel 배포를 사용합니다. 기능 이전 코드로 롤백하면 신규 여행에 명시 PIN 환경변수가 다시 필요합니다.


### 공금·개인 지출 통계

지출 통계에서 공금·개인·미지정의 원화 순지출, 집계 건수, 전체 대비 비율을 비교합니다. Notion `비용구분`의 `공동`(또는 `공금`)은 공금으로, `개인`은 개인으로 집계하고 비어 있거나 다른 값은 미지정으로 분리합니다. 세 구분의 합계는 같은 기간의 전체 순지출과 일치합니다. 환불도 건수에 포함합니다.

기존 결제완료·원화 환산·중복 제거·결제일/도시 시간대 조건을 그대로 적용하며 환산 불가 항목은 합계에서 제외합니다. 공금/개인 카드를 선택하면 그 구분의 항목별 금액·비율을 표시합니다. 차트/항목을 선택하거나 구분별 내역 보기를 누르면 같은 기간·비용구분·분류로 지출 내역을 엽니다. 상단 예산 사용률과 잔여 예산은 선택 기간의 전체 지출을 여행 전체 예산과 비교하는 기존 기준입니다. 공금 잔액이나 참여자별 분담금을 계산하지 않습니다.

환불이 구분별 지출을 초과하면 해당 금액은 음수로 표시하고 전체 대비 비율은 숨깁니다. 각 구분의 항목별 차트도 기존 음수 항목 검증을 독립적으로 적용합니다. 집계 항목이 없는 구분은 `—`, 실제 순지출이 0인 구분은 `₩0`으로 구별합니다.
