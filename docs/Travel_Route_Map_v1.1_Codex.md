# My Travel Hub — 일정 기반 동선 지도 v1.1

> Codex 전달용 구현 명세서 · 2026-11-25
> Repository: https://github.com/shin02160/travel
> 기준: `main` 브랜치에서 확인한 Notion 읽기 전용 앱 구조 및 사용자가 제공한 동선 지도 참고 이미지

## 1. 구현 목표

기존 여행 일정 데이터를 활용하여 실제 지도 위에 날짜별 방문 장소를 번호 마커로 표시하고, 방문 순서대로 직선 점선을 연결한다. 사용자는 여행의 이동 흐름과 장소 간 위치 관계를 한눈에 확인할 수 있어야 한다.

참고 이미지의 핵심은 **원형 번호 마커 + 장소 간 점선 + 실제 지도 배경**이다. 실제 도로를 따라가는 길찾기가 아니다. 기존 일정 타임라인과 동일한 데이터를 사용하며, 별도의 동선 일정을 중복 등록하지 않는다.

### 1.1 구현 범위

- 여행 상세 > 일정 탭에 `타임라인 / 동선 지도` 보기 전환 추가
- 날짜별 지도 및 여행 전체 지도 제공
- 일정 시간순 번호 마커 및 직선 점선 표시
- 날짜별 마커 색상 구분, 지도와 일정 목록의 양방향 선택 연동
- 좌표 누락, 취소 일정, 같은 장소 재방문, 동일 시간, 국가·도시 간 이동 처리
- 실제 지도 확대/축소 및 모든 표시 대상에 대한 자동 지도 범위 조정
- Notion 새로고침 시 동선 데이터 재계산
- 모바일/PC 반응형, 기존 PIN 인증 및 읽기 전용 정책 유지

### 1.2 제외 범위

- 실제 도로 기반 경로 계산, 이동거리·소요시간 산출, 최단 경로 및 순서 최적화
- 실시간 위치 추적, GPS 이동기록, 내비게이션, 오프라인 지도
- 앱에서 Notion 일정 또는 좌표 수정·등록
- 별도 장소 DB 신설, 여행별 하드코딩, 기존 일정 탭 전면 재설계
- 자동 지오코딩 서비스 신규 연동은 필수 범위가 아님. §4.4 참조.

## 3. UI/UX 요구사항

### 3.1 메뉴 및 화면 구조

기존 상위 탭의 순서와 명칭을 유지한다. `일정` 탭 내부에만 보기를 추가한다. 기본 화면은 기존 `타임라인`이다.

```text
여행 상세
  개요 | 오늘 일정 | 일정 | 예약 | 예산 | 지출 | ...
                      ┌─────────────────────────────┐
                      │ [타임라인] [동선 지도]       │
                      │ [전체] [12/5] [12/6] ...     │
                      │ 지도 표시 3/4 · 위치 미확인 1 │
                      │ ┌─────────────────────────┐ │
                      │ │ 실제 지도               │ │
                      │ │  ① ··· ②               │ │
                      │ │         ··· ③          │ │
                      │ │                    + / − │ │
                      │ └─────────────────────────┘ │
                      │ 직선 연결 · 실제 경로 아님   │
                      │ ① 11:30  마카오 국제공항    │
                      │ ② ...    숙소              │
                      │ ③ ...    공연장            │
                      │ 위치 미확인 일정 1건         │
                      └─────────────────────────────┘
```

위 장소명은 UI 설명을 위한 예시이며 실제 좌표 또는 일정 데이터로 하드코딩하지 않는다.

### 3.2 날짜 및 보기 상태

- 동선 지도 첫 진입: 여행 현지 오늘이 여행 기간 안이면 오늘, 아니면 여행 시작일. 날짜가 비정상/누락된 경우 일정의 유효 날짜 중 첫 날짜. 날짜가 없으면 명확한 빈 상태 표시.
- `전체` 선택 가능. 날짜 버튼은 여행 기간 기준으로 동적으로 생성하고 모바일에서는 가로 스크롤을 허용한다. 여행 기간 밖 일정은 조용히 폐기하지 말고 별도 일자 또는 오류 안내로 표시한다.
- 날짜를 선택하면 지도, 마커, 점선, 일정 목록 및 집계가 함께 갱신된다.
- 여행별 보기 모드와 선택 날짜를 유지하고 다른 여행에 섞이지 않게 한다. 기존 hash 라우팅과 sessionStorage 정책을 존중한다. 잘못된 저장 상태는 기본값으로 복구한다.
- 기존 타임라인 검색을 유지한다. 지도는 기본적으로 해당 날짜 전체 동선을 표시하며 타임라인의 제목 검색어에 의해 숨겨지지 않게 한다. 지도에 검색 기능을 별도로 추가하지 않는다.
- 지도는 동선 지도 보기 진입 시에만 마운트/로드한다. 타임라인 복귀, 여행 변경, PIN 만료 시 지도 인스턴스를 정리한다.

### 3.3 지도 표현

- 지도 배경: 실제 지리 정보가 표시되는 지도 타일. 예시 이미지/가짜 지도를 운영 화면으로 사용하지 않는다.
- 원형 번호 마커: 약 28~34px, 날짜별 배경색, 대비 높은 숫자, 흰색 테두리. 방문 순서는 일자별 1부터 시작하며 전체 보기에서도 날짜별로 번호를 유지한다.
- 점선: 두 방문지의 좌표를 잇는 직선 Polyline, 약 2~3px, `dashArray: '6 6'` 수준의 디자인. 전체 보기에서는 날짜별 색상을 구분하고 날짜가 다른 구간은 연결하지 않는다.
- 지도 하단에 항상 `점선은 방문 순서를 나타내며 실제 이동 경로가 아닙니다.` 안내를 표시한다.
- 일자별 색상 예시: Day 1 `#B6E876`, Day 2 `#B9B0ED`, Day 3 `#F4B9A5`, Day 4 `#A9D6F4`; 이후 날짜도 결정적 팔레트로 배정. 색상만으로 구분하지 않고 날짜 범례/번호를 함께 제공한다. 실제 선 색상과 텍스트는 배경 대비를 검토한다.
- 자동 범위: 해당 날짜의 유효 좌표 전체를 `fitBounds`로 포함. 1개는 적당한 확대 수준, 0개는 빈 상태. 날짜를 변경할 때 재설정하되 마커 선택 때 불필요하게 전체 확대를 재실행하지 않는다.
- 가까운 장소의 마커가 겹치면 묶음/펼치기(spiderfy 등) 또는 선택 가능한 번호 목록을 제공한다. 좌표가 같은 마커를 임의로 다른 지리적 위치에 저장하지 않는다. 필요하면 시각적 오프셋과 실제 위치 연결선을 사용한다.
- 지도 줌, 드래그, 범위 재설정 버튼 제공. 기본 화면 진입 시 위치 권한을 요청하지 않는다.

### 3.4 지도와 일정 목록 연동

- 지도 마커 선택: 번호, 날짜/시간, 일정명, 장소, 상태를 팝업으로 표시하고 대응 목록 항목을 강조한다.
- 목록 선택: 해당 마커로 지도 이동 및 팝업 열기. 좌표가 없는 일정 선택 시 위치 미확인 안내, 허용된 `지도 URL`이나 `Notion 원본` 링크를 제공한다.
- 취소 일정은 지도/점선 대상에서 제외한다. 기존 일정 화면에서 취소 상태를 볼 수 있어야 한다.
- 시간 미정 일정, 좌표 누락 일정, 이동 구간 기록 등 지도에 그릴 수 없는 일정도 별도 목록 또는 표시 상태로 확인할 수 있어야 한다.
- 링크는 기존 URL 검증 규칙을 재사용한다. 외부 링크 `target="_blank"`와 `rel="noopener noreferrer"` 적용.

### 3.5 반응형 및 접근성

- 모바일: 보기 전환 → 날짜 선택 → 지도(약 320~420px, 화면 크기에 맞춰 조정) → 일정 목록 순서. 지도 조작 중 페이지 스크롤 충돌을 최소화한다.
- PC: 공간이 충분하면 지도와 방문 목록을 좌우로 배치하되 기존 상세 메뉴 및 레이아웃을 보존한다.
- 키보드로 날짜/보기/목록을 선택할 수 있어야 한다. 선택 상태를 `aria-pressed` 또는 적절한 tab 패턴으로 제공한다. 마커에는 접근 가능한 이름을 부여하고 지도 없이도 동선 목록을 이해할 수 있도록 한다.
- 지도 타일 출처 표시는 가리지 않는다. 지도 실패 시에도 목록/타임라인 이용 가능.

## 4. Notion 데이터 계약

### 4.1 기존 DB 재사용

대상: My Travel Hub > `여행 일정` DB. 기존 `여행` relation 및 모든 기존 속성을 유지한다.

| 속성 | 타입 | 지도 활용 |
|---|---|---|
| 일정명 | 기존 제목 | 단일 장소의 짧은 이름 또는 간결한 이동 구간 |
| 활동 | 텍스트(RICH_TEXT), 추가 완료 | 타임라인의 활동 및 마커 상세 |
| 동선 순서 | 숫자(Number), 추가 완료 | 시간 미정 계획의 명시적인 일자별 상대 순서 |
| 메모 | 기존 텍스트 | 상세 교통편·참고 정보, 기존 값 보존 |
| 일시 | 기존 날짜 | 날짜 및 방문 순서 |
| 구분 | 기존 선택 | 일정 분류 |
| 장소 | 기존 텍스트 계열 | 장소 표시 |
| 진행상태 | 기존 상태/선택 | 취소 제외 등 |
| 지도 URL | 기존 URL | 지도 링크 및 확정 좌표 추출 후보 |
| 관련 예약 | 기존 relation | 예약 확인용; 좌표를 임의로 대체하지 않음 |
| 위도 | 숫자(Number), 추가 완료 | WGS84 위도 |
| 경도 | 숫자(Number), 추가 완료 | WGS84 경도 |

`위도`, `경도`, `활동`, `동선 순서`는 운영 DB에 추가되어 있다. 코드에서는 네 속성을 **선택적**으로 지원하여 DB에 없거나 값이 비어 있어도 기존 API가 실패하지 않게 한다. 별도 장소 DB는 만들지 않는다. `동선 순서`는 시각이 없는 계획의 상대 순서를 보존할 때만 필요하다.

Notion 스키마 추가 및 기존 일정 정비는 별도 작업으로 수행하였다. 미확인 좌표의 추가 입력은 별도 작업으로 처리한다. Codex는 DB를 자동 수정하지 않는다. 기존 읽기 전용 토큰을 쓰기 가능하도록 변경하지 않는다.

### 4.2 API 매핑 제안

`server/notion-trips.js`의 `scheduleDetails(page)`에서 지도 좌표, `activity` 및 `routeOrder`를 추가한다. 기존 `fields` 구조, 인증, `mapUrl`, 메모, 관련 예약을 유지한다.

```js
// 기존 schedule row에 선택적으로 추가되는 정규화 데이터 예시
{
  id: 'schedule-page-id',
  title: '방문 장소명',
  activity: '체크인',
  routeOrder: null, // 양의 정수 또는 null
  fields: { 일시: '2026-12-05T11:30:00+08:00', 구분: '이동', 장소: '장소명', 진행상태: '예정' },
  date: { start: '2026-12-05T11:30:00+08:00', end: null, timeZone: null },
  mapUrl: null,
  sourceUrl: null,
  bookingIds: [],
  note: null,
  coordinates: { lat: 22.0, lng: 113.0, source: 'notion' }
}
```

수치는 데이터 형태를 설명하기 위한 임의 값이다. 운영 마커 위치로 사용하지 않는다. 값이 없거나 신뢰할 수 없으면 `coordinates: null`을 반환한다.

검증: 유한한 숫자만 허용, 위도 -90~90/경도 -180~180, 두 값 모두 필요. `0`은 유효 숫자로 처리하고 빈 문자열/null을 0으로 변환하지 않는다. 지도 렌더링 시 타일 투영이 허용하는 범위 밖 좌표는 별도 표시하고 지도 중심으로 강제 보정하지 않는다.

### 4.3 좌표 출처 우선순위

1. Notion에 등록된 유효한 WGS84 위도·경도 쌍.
2. 허용된 기존 지도 URL에서 **대상 장소 좌표임이 명시되고 좌표계가 확인된 경우에만** 추출. 예: Google Maps의 좌표 검색 URL에서 명시적인 좌표 쌍. 지도 카메라 중심(`@lat,lng`), 경로 출발/도착 혼용, 검색 결과 중심, 불명확한 링크는 대상 장소로 간주하지 않는다.
3. 나머지는 위치 미확인(`coordinates: null`). 단축 URL은 v1에서 자동 추적하지 않으며, 사용자가 외부 지도에서 열 수 있게 한다.

기존 `savedMapUrl()`의 허용 목록을 우회하지 않는다. 사용자 입력 URL에 서버가 임의로 접근하는 방식은 금지한다. 좌표 해석이 불명확하면 그리지 않는다. 중국 본토의 GCJ-02, Baidu BD-09 좌표를 WGS84로 간주하지 않는다. 좌표계가 불명확한 경우 수동 확인 대상으로 분류한다.

### 4.4 자동 좌표 검색 관련 범위 결정

v1.1의 필수 기능은 등록된 좌표/확정 좌표 URL을 이용한 **자동 지도 생성**이다. 장소명만 있는 기존 일정의 좌표를 일괄 자동 확정하는 기능과는 구분한다.

장소명 검색이 필요하면 차후 승인된 지오코딩 서비스로 후보 좌표를 조회하고 사용자가 지점을 검증한 뒤 Notion에서 좌표를 입력하는 방식으로 확장한다. 지명만으로 다른 도시의 동일 상호, 공항 터미널, 체인점 지점을 자동 확정하지 않는다. 공용 Nominatim에 일정 전체를 반복 일괄 요청하거나 브라우저 자동완성으로 사용하지 않는다. 지도/검색 서비스의 사용 조건 및 저장·캐시 제한을 확인한다.

## 5. 일정 → 동선 생성 로직

### 5.1 공통 데이터 처리

권장 신규 순수 함수: `buildRouteModel(scheduleRows, { date, zone, now })`.

- 기존 `planDay()`의 날짜/시간 처리 방식을 기준으로 삼고, 기존 `Timeline()`의 정렬과 차이가 있는 경우 동일 일자 내 순서 기준을 공통화한다. 날짜 필터는 원본 일정의 현지 일자 정책을 따른다. 다른 시간대를 임의 추정하지 않는다.
- 여행 시작/종료, 일정 시작 시간, 시간대 유효성을 검증한다. 완료 일정은 포함, 취소 일정은 제외한다. 날짜 미정 항목은 전체 보기의 미분류 목록에서만 표시한다.
- 일자별 확정 시간 일정에 방문 순서를 부여한다. 같은 시간은 안정적이며 재조회에도 결과가 변하지 않는 보조 기준(예: 일정 ID)을 적용한다. 실제 방문 순서를 알 수 없는 동시각 일정은 안내하고, 그 그룹의 불확실한 구간은 연결하지 않는다.
- 시간 미정/종일 일정은 명시적 동선 순서가 있고 순서의 상대 관계가 검증되는 경우 계획 번호와 점선을 표시한다. 그렇지 않으면 번호 없는 보조 마커로 표시하고 점선 경로에는 넣지 않는다. 목록에는 `시간 미정` 또는 `종일` 표시. 상세 우선순위는 §12 참조.
- 구분이 `이동`이어도 도착 지점 좌표가 명확하면 장소 마커로 포함 가능하다. 단일 좌표가 출발인지 도착인지 불명확한 `공항→호텔`, `역→역` 등은 이동 기록으로만 표시하고 문자열을 쪼개서 좌표를 추측하지 않는다.
- 원본 일정은 모두 보존한다. 연속된 동일 시설 방문은 화면상의 한 방문 그룹으로 묶고, 중간에 다른 장소가 있으면 별도의 재방문 번호를 유지한다. 단순히 좌표가 가깝다는 이유만으로 합치지 않는다. 상세 기준은 §12 참조.
- 번호는 시간순 방문 후보를 기준으로 부여한다. 좌표 누락이 있어도 후속 번호를 당겨 재정렬하지 않는다. 예: ① 정상, ② 위치 미확인, ③ 정상 → 지도에는 ①/③, 목록에는 ①/②/③.
- 누락/불확실 구간을 건너뛰고 ①→③을 그리지 않는다. 유효한 연속 방문 사이에만 선을 연결한다. 명시적 이동 기록은 별도 타임라인 행이며 방문 번호를 소비하지 않는다. 양쪽 방문이 확인된 단순 이동 행은 연결을 끊지 않는다. 중간 경유지가 불명확하거나 위치 미확인 방문이 있는 경우에는 연결을 끊는다.
- 날짜가 다른 구간 사이에는 선을 그리지 않는다. 같은 날짜의 도시·국경 간 구간은 계획상 연속 방문이고 좌표가 확정된 경우 직선 연결 가능하다. 실제 도로, 항공, 철도 경로로 표시하지 않는다.
- 좌표/시간 미확인/취소/날짜 미정/이동 기록 등의 사유를 목록과 지도 표시 집계에서 구분한다.

### 5.2 출력 구조 예시

```ts
// 개념적 타입. 기존 JS 프로젝트에 TypeScript 도입할 필요 없음.
type RoutePoint = {
  id: string; date: string; time: string | null;
  number: number | null; title: string; location: string | null;
  lat: number; lng: number; color: string;
};
type RouteSegment = { date: string; fromId: string; toId: string; color: string };
type RouteModel = {
  dates: string[];
  points: RoutePoint[];
  segments: RouteSegment[];
  // 원본 일정 ID, 번호, 사유, 지도 표시 여부 등을 포함하는 목록
  rows: object[];
};
```

지도 컴포넌트는 모델의 결과만 렌더링한다. 좌표 검증·일자 분류·번호·연결 여부를 지도 라이브러리 내부에서 중복 계산하지 않는다.

## 6. 기술 구현 제안

### 6.1 라이브러리

권장: **Leaflet + 적합한 지도 타일 공급자**. React-Leaflet은 React 19와 호환되는 버전이 확인될 경우 사용 가능하며, 그렇지 않으면 Leaflet을 React `useEffect`/ref로 연동한다. 의존성 버전은 현재 프로젝트의 Node/Vite/React와 호환되는 것으로 확정하고 lockfile을 갱신한다.

- `L.divIcon`: 번호 마커
- `L.polyline`: 직선 점선, 라우팅 API 호출 없음
- `L.latLngBounds` / `fitBounds`: 날짜별 자동 범위
- `L.tileLayer`: 실제 지도 배경 및 attribution
- 팝업은 DOM `textContent` 또는 안전한 React 렌더링을 사용한다. Notion 문자열을 HTML로 직접 삽입하지 않는다.

Leaflet: https://leafletjs.com/reference.html
OpenStreetMap 타일 정책: https://operations.osmfoundation.org/policies/tiles/
Nominatim 사용 정책(참고): https://operations.osmfoundation.org/policies/nominatim/

**지도 라이브러리와 타일 제공 서비스는 별개**다. 실제 길찾기 API는 사용하지 않지만 타일/지오코딩은 공급자에 따라 제한·요금이 있을 수 있다. OSM 기반 타일은 정책에 적합한 경우에만 사용한다. 공급자 선택은 비용, 이용약관, 모바일 성능, 마카오·중국 본토에서의 연결성 및 좌표 정합성 검증 후 확정한다. 무료/무제한 또는 중국 내 정상 동작을 보장한다고 명시하지 않는다. 타일 공급자를 교체할 수 있게 설정을 분리한다. 비밀 키를 `VITE_` 환경변수에 저장하지 않는다.

### 6.3 보안 및 성능

- 기존 `/api/trips/:tripId` PIN 확인, HttpOnly 세션, 여행 관계 필터, `Cache-Control: private, no-store` 유지. PIN 없이 접근 가능한 목록에 좌표·방문 상세를 포함하지 않는다.
- 여행 상세 지도는 인증 이후 받은 데이터만 사용한다. 외부 타일 제공자에게 일정 제목·메모·PIN·Notion 토큰을 전송하지 않는다. 타일 요청에 의해 지도 조회 영역/IP가 노출될 수 있으므로 공급자 선택 시 고려한다.
- 지도 초기화는 한 번만 수행하고 날짜 변경은 레이어 갱신으로 처리한다. React lifecycle에 맞춰 인스턴스/리스너 해제, 지도 컨테이너 크기 변경 시 `invalidateSize` 처리.
- 지도 표시 모드에 진입하기 전 지도 타일 요청을 보내지 않는다. 여행 변경/로그아웃/인증 실패 시 이전 여행 지도와 선택 상태를 즉시 제거한다.
- 지도 오류, 타일 오류, 좌표 오류가 전체 일정 조회 실패로 전파되지 않도록 격리한다.
- 정확한 여행 일정/좌표를 콘솔, 공개 저장소 샘플, 공개 캐시 등에 남기지 않는다.

## 8. 구현 순서 (Codex 작업 지시)

1. 최신 브랜치/작업 트리, README, `main.jsx`, 현재 일정 데이터 계약과 관련 테스트를 확인한다. 사용자 변경분을 덮어쓰지 않는다.
2. 좌표 매핑과 검증 순수 함수를 구현한다. Notion 속성이 없을 때의 호환성 및 기존 지도 링크 규칙을 먼저 테스트한다.
3. 날짜별/전체 동선 모델을 구현하고 순서, 결측, 취소, 중복, 일자 간 연결 금지 테스트를 작성한다.
4. 지도 라이브러리/타일 공급자 설정을 추가하고, 번호 마커·점선·팝업·자동 범위·겹침 처리를 구현한다.
5. `NotionTravel.jsx`의 일정 탭에서 보기 전환을 연결하고 지도/목록 동기화 및 여행별 상태 보존을 적용한다.
6. 오류 상태, 반응형 UI, 접근성, PIN 만료 및 여행 전환을 검증한다.
7. 전체 회귀 테스트, lint, build를 실행하고 README에 운영 설정, Notion 좌표 등록 절차, 지도/좌표계 제약을 기록한다.

개발은 별도 브랜치(예: `codex/schedule-route-map-v1`)에서 진행할 것을 권장한다. 사용자 승인 없는 운영 배포·Notion 스키마 변경·유료 API 계약은 하지 않는다.

| AC-09 | 취소/시간 미정 | 취소 제외, 명시적 순서 없는 시간 미정은 번호 없는 별도 표시, 원본 일정 보존 |
| AC-10 | 자동 지도 범위 | 날짜 변경 시 전체 유효 장소 포함; 0/1개 처리 정상 |
| AC-11 | 모바일/PC | 화면 깨짐/가로 오버플로 없음, 지도와 목록 조작 가능 |

| AC-14 | 보안 회귀 | PIN 없는 상세 조회 차단, 만료/여행 간 격리, 공개 목록에 좌표 없음 |
| AC-15 | 기존 DB 호환 | 신규 속성 미등록/미입력이어도 기존 여행 상세 및 API 정상 |
| AC-16 | 실제 경로 오인 방지 | 직선 점선 안내 노출, 거리·ETA·길찾기 API 미사용 |
| AC-17 | 기존 기능 회귀 | 예약/지출/예산/체크리스트/쇼핑/오늘 일정/정보 기능 회귀 없음 |

### 9.1 필수 자동 테스트

- 정상 좌표, 0 좌표, 누락, 문자열, 범위 초과 및 `NaN` 등 좌표 검증
- 확정 좌표 URL과 카메라 중심 URL, 단축 URL, 악성 URL, 좌표계 불명확 URL 구분

## 11. 전달 시 확정 사항과 검토 필요 사항

**확정된 요청:** 첨부 참고 이미지와 같이 실제 지도에 번호 마커와 직선 점선으로 일정 동선을 표시한다. 실제 길찾기는 필요하지 않다. 기존 Notion 일정 중심 관리 방식을 유지한다.

**설계 제안:** 일정 탭 내부 보기 전환, Leaflet, 날짜별 색상 및 번호, 전체 보기, Notion 좌표·활동·동선 순서 속성, 보수적인 좌표 해석 정책은 구현을 위한 권장안이다. 지도 공급자와 구체적인 스타일은 실제 환경 검증 후 확정한다.

**현재 미확인:** 일부 좌표의 정확성 및 미등록 좌표, 지도 타일 서비스 이용 조건 및 현지 접속성, 실제 배포 화면에서의 동작. Notion 데이터 변경은 §12에 명시된 범위까지 완료했다. GitHub 코드 수정, 테스트 실행 및 배포는 수행하지 않았다.


## 12. v1.1 변경 요구사항 — 장소 중심 일정 및 활동 분리 (우선 적용)

본 절은 v1.0 대비 변경사항이다. 상충되는 기존 문구가 있다면 본 절을 우선한다.

### 12.1 운영 데이터 계약

기존 Notion 여행 일정 DB의 활동(rich_text), 동선 순서(Number), 위도/경도(Number)를 선택적으로 읽는다. 실제 운영 DB 식별자, 여행별 장소와 날짜, 일정/좌표 채움 현황은 공개 명세에 복사하지 않는다. 기존 원본 행 ID·일시·메모·예약 관계·여행 관계를 유지하며, 좌표와 상대 순서가 불완전해도 조회에 실패하지 않는다. 현재 검증 범위는 QA 보고서를 따른다.

### 12.2 일정 등록 및 표시 원칙

| 속성 | 입력 규칙 |
|---|---|
| 일정명 | 장소명 (방문) 또는 출발지 → 도착지 (이동 구간) |
| 활동 | 방문 목적, 체크인, 공연명, 교통편 번호 등을 유지 |
| 장소 | 해당 지점의 정확한 명칭 및 현지 주소. 이동 구간은 기존 전체 경로 문자열 보존 |
| 일시 | 실제/계획 일시 유지. 시간이 없으면 날짜만 등록 |
| 동선 순서 | 시각 미정이나 상대 순서가 명확한 경우만 10, 20, … 등 양의 정수로 기록 |
| 메모/관련 예약 | 상세 이동 방법 및 참고사항은 메모, 예약 상세는 기존 관계형 연결 |

타임라인: 장소명(제목) + 활동(보조 텍스트) + 시간 + 분류 + 상태. 상세 펼치기에서 메모, 장소 주소, 지도 URL, 연결 예약, 원본 링크. 오늘 일정/다음 일정 카드에도 활동 표시. 신규 속성이 없는 기존 일정은 원래 제목을 그대로 렌더링하고 빈 활동을 중복 표시하지 않는다.

지도: 방문 번호와 짧은 장소명. 팝업/목록에서 활동, 시간, 상태, 상세 정보를 확인. 지도와 목록은 동일한 방문 그룹 모델을 사용한다. 기존 일정 검색은 제목과 활동을 대상으로 확장하되 지도 동선 전체를 검색으로 숨기지 않는다.

### 12.3 방문 그룹과 이동 구간 모델

- 단일 장소 일정과 이동 구간 행을 분리한다. 제목/장소에 명시적인 구간 구분자(`→`)가 있고 복수 장소가 포함된 행은 이동 구간으로 분류한다. 모든 `구분=이동` 행을 제외하면 안 된다(공항 도착, 역 탑승, 국경 통과는 방문 지점).
- 장소가 단일 시설이고 이동 행 사이에 다른 방문이 없다면 양쪽 방문 지점 사이에 점선을 연결한다. 이동 행은 독립 번호나 마커를 생성하지 않는다. 구간 내부의 경유지를 문자열 분해하여 지오코딩하거나 시각을 추정하지 않는다.
- 같은 날 연속되는 동일 장소의 활동은 하나의 방문 그룹으로 표시하되 `eventIds`와 원본 활동 목록을 유지한다. 동일 장소 확인은 정규화된 정확한 장소명/주소 또는 확인된 동일 시설 대표 좌표로 판단한다. 서로 다른 장소의 좌표가 우연히 가까우면 묶지 않는다. 시설 내 매장은 같은 시설 대표 좌표이고 동일 시설 소속임이 명확한 경우만 그룹화. 불명확한 경우 겹침 UI 처리. 다른 방문이 끼면 재방문 번호 유지.
- 집/귀가로만 식별되는 사적 장소는 기본 지도 제외, 원본 타임라인 유지. 지역 전체나 다중 상권 후보는 임의 중심 좌표 생성 금지.
- 중복 가능성이 있는 일정(예: 동일 매장에 대한 선택 방문)은 자동 삭제하지 않는다. 같은 시설 내 연속 활동은 지도 그룹으로 처리하고 타임라인 원본 보존.

### 12.4 방문 순서 규칙

1. 일자별 방문 후보를 먼저 분류하고 취소·순수 이동·사적 집 일정을 제외한다. 위치 누락인 단일 장소 후보는 목록에 남긴다.
2. 유효한 `routeOrder`를 명시한 방문은 이 값 오름차순을 우선한다. 숫자 자체는 내부 정렬 키로 사용하며 표시 번호는 1부터 연속 부여한다. 시간 미정은 명시하고 계획 순서임을 표시한다. 실제 시간과 충돌하면 경고하되 명시 순서에 따라 연결한다. 중복 순서는 해당 방문 앞뒤 구간만 보류한다.
3. 혼합 일자에서도 유효한 명시 순서 구간은 유지한다. 시각만 있는 방문은 모든 명시 순서 기준점의 시각이 유효하고 단조 증가할 때만 시각 기준으로 배치한다. 상대 관계가 미확정이면 보조 표시하고 다른 정상 구간을 차단하지 않는다. 명시 순서 없는 동시각 방문의 불확실성은 해당 구간에만 적용한다. 페이지 생성순이나 UUID를 실제 순서로 간주하지 않는다.
4. 정렬 후 연속 동일 시설 방문을 그룹화하고 번호를 부여한다. 위치 미확인 그룹도 번호를 보존한다. 누락 지점 전후를 가로질러 점선을 이어 그리지 않는다. 날짜 사이 선 연결 금지.
5. 기존 `tripCalendar`가 특정 여행 ID만 시간대에 매핑하는 제한을 점검한다. 날짜만 기록된 값은 날짜 그대로 취급하고, 명시된 오프셋 및 현지 날짜 기준을 일관되게 적용한다. 여행별 하드코딩을 새로 추가하지 않는다. 시간대가 없을 때는 확인 필요 상태 표시.

### 12.5 구현 세부 및 추가 QA 수용 기준

- `scheduleDetails()`에서 `activity`(문자열/null), `routeOrder`(양의 안전 정수/null), `coordinates`(유효 좌표쌍/null)를 선택적으로 매핑한다. Notion 속성의 타입을 검증하고 빈 문자열을 0으로 치환하지 않는다. 기존 API 응답과 PIN 격리, no-store 유지.
- `buildRouteModel`에서 `visitGroups`, `eventIds`, `segments`, `unmapped`, `unordered`, `transfers` 등을 분리하고 표시 집계 단위를 일정 건수와 방문 그룹 수로 구분한다.
- `Timeline`/`TodayDashboard`는 activity를 보조 제목으로 표시하고, 명시 순서가 있는 날짜 전용 일정은 시간 미정으로 정렬 표시한다. 기존 타임라인 상세 기능을 유지한다.
- 새 날짜나 여행을 추가해도 코드 수정 없이 동작해야 한다. 12월 6일 예시는 일반화된 테스트 fixture로 검증하며 실제 사용자 장소/좌표 하드코딩 금지.

| ID | 추가 검증 항목 | 합격 기준 |
|---|---|---|
| AC-18 | 장소/활동 분리 | 제목과 활동이 분리 표시되고 기존 메모·예약 유지 |
| AC-19 | 이동 구간 | 복수 장소 이동 행은 번호 미생성, 확인된 양쪽 방문 연결 |
| AC-20 | 연속 동일 장소 | 한 마커 및 하위 활동 전부 표시, 원본 행 유지 |
| AC-21 | 재방문 | A→B→A는 서로 다른 방문 번호 3개 |
| AC-22 | 시간 미정 계획 | 모두 명시 순서가 있으면 10~80을 1~8로 표시, 시각 추정 금지 |
| AC-23 | 불완전 순서 | 순서 중복·누락·시간 충돌 시 경고/보조 표시 및 임의 연결 금지 |

### 12.6 미완료 데이터 및 배포 전 확인

일부 식당·숙소·국경 시설·관광지 좌표는 아직 비어 있다. 기존 이동 일정의 모든 출발·도착 지점이 독립 방문으로 분리된 것은 아니다(주요 이동 지점부터 보완 중). 지도 기능은 이를 누락 안내로 처리하며, 완전한 동선 표시에는 후속 데이터 보완이 필요하다. 좌표 검색 결과의 정확한 지점 및 WGS84 여부를 확인하고 기존 값을 덮어쓰기 전에 비교한다. 중복 일정은 별도 사용자 확인 없이 삭제하지 않는다. 지도 타일의 라이선스/비용/중국 내 접속성을 확인한다. Codex는 Notion 쓰기나 배포를 별도 승인 없이 수행하지 않는다.

## 13. 일정 타임라인 UI 추가 개정 (2026-11-25)

이 절은 사용자의 추가 요청이며, 원본 행 단위 타임라인을 유지한다는 이전 문구보다 우선한다. 지도에 사용하는 방문 그룹 모델을 일정과 오늘 일정에도 공통 적용한다. Notion 원본 행은 삭제하거나 수정하지 않는다.

1. 보호된 Notion API 응답에 `activity`, `coordinates`(위도·경도), `routeOrder`를 선택적으로 제공한다. 기존 PIN·여행 격리·읽기 전용 계약을 유지한다.
2. 타임라인을 방문 장소 중심의 카드로 재구성한다.
3. 이동 구간은 별도의 대형 카드가 아니라 확인된 방문 사이의 작은 연결 행으로 표시한다. 위치가 불명확한 기록은 별도 미확정 연결 기록으로 남기며 임의로 끼워 넣지 않는다.
4. 일정명 아래 활동을 기본 노출한다.
5. 중복 장소명 및 상세 주소는 접힌 기본 화면에서 숨기고 펼친 상세에 보존한다.
6. 날짜는 일자별 헤더에만 표시한다. 개별 카드와 연결 행에는 시간/실제 시간 범위/시간 미정/종일만 표시하고 시각을 추정하지 않는다. 상세의 원본 일시는 보존한다.
7. 연속된 동일 장소의 활동은 지도와 동일한 방문 그룹의 카드 하나로 표시하고 하위 활동 전체를 유지한다. 다른 방문이 끼는 재방문은 분리한다.
8. 모바일 카드 높이와 여백을 줄인다. 상세 펼치기 및 링크·장소 복사의 키보드 접근성을 유지한다.
9. 모든 원본 일정의 상세·메모·주소·예약 관계 및 상태를 펼친 상세에서 확인할 수 있어야 한다. 취소/사적 장소 등 지도 제외 기록도 원본 상세를 보존한다.
10. 일정 탭과 오늘 일정 탭은 동일한 데이터 가공 및 렌더러를 사용한다. 다음 일정 카드도 활동과 시간만 기본 노출한다.
11. 동선 지도와 타임라인의 방문 그룹/번호/순서를 일치시킨다. 검색은 전체 모델 구성 후 그룹 단위로 적용하며, 검색 때문에 그룹을 쪼개거나 방문 번호를 다시 부여하지 않는다.

### 13.1 추가 수용 기준

- 동일한 날짜의 일정/오늘 일정/지도에 같은 방문 그룹 ID와 순서가 나온다.
- A의 연속 활동 2건은 한 카드, A→B 이동은 작은 연결 행, A→B→A는 3개 방문 카드다.
- 기본 summary에는 주소·메모·개별 YYYY-MM-DD가 없고 장소명과 활동이 구분된다.
- 펼치면 모든 하위 원본의 메모·상태·예약·원본/지도 링크·주소가 남아 있다.
- 활동 검색으로 그룹의 일부만 일치해도 원래 그룹의 하위 활동과 번호를 유지한다.
- 순서를 입증할 수 없는 이동/집/취소 기록은 버리지 않고 압축된 기록으로 제공한다.
- 390px 모바일에서 페이지 가로 넘침이 없고 방문 카드·연결 행을 키보드로 펼칠 수 있다.
